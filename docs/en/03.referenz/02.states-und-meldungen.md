## Where do I find yesterday, last week, last month (previous states)?

<!-- abschnitt: prio=A; gewicht=25; readme=partial; cluster=periods-13,periods-14; features=current-year-previous,output-basic-period-states,rollover-previous-timestamps,output-cost-vs-earnings,rollover-midnight-cron,output-tree-layout,output-cumulative-reading,output-statistics-json,output-info-price-states,output-state-deletion,output-timestamps-ack -->
<!-- muss beantworten: previous*-States, Zeitstempel, wann sie gefüllt werden; Kosten/Einnahmen. -->

**In short:** Completed periods are stored under `sourceanalytix.0.<device>.currentYear.<category>` in the states `01_previousDay` (yesterday), `02_previousWeek` (last week), `03_previousMonth` (last month), `04_previousQuarter` (last quarter) and `05_previousYear` (last year). They are filled at the period rollover at midnight, so only after the first rollover, and only if "Previous period" is switched on in the instance.
<!-- quelle: code=main.js:23@v0.6.1; code=main.js:2379-2403@v0.6.1; code=admin/jsonConfig.json:93-101@v0.6.1; issue=#137; forum=217254; forum=224702 -->

### Where the states are

`<category>` depends on what you switched on for the datapoint and on whether the price definition describes costs or earnings:

| Folder under `currentYear` | Content | When it exists |
|---|---|---|
| `consumed` | Consumption | "Calculate consumption" on, price definition of type Costs |
| `delivered` | Feed-in or generation | "Calculate consumption" on, price definition of type Earnings |
| `costs` | Costs | "Calculate costs" on, price definition of type Costs |
| `earnings` | Earnings | "Calculate costs" on, price definition of type Earnings |
| `meterReadings` | Meter reading at the end of the period | "Store Meter Values" on |
<!-- quelle: code=main.js:1977-1978@v0.6.1; code=main.js:2390-2401@v0.6.1; code=admin/jsonCustom.json:129-137@v0.6.1 -->

Each of these folders has the same five previous-period states. For example, yesterday's electricity consumption is in `sourceanalytix.0.<device>.currentYear.consumed.01_previousDay`, and the matching costs are in `sourceanalytix.0.<device>.currentYear.costs.01_previousDay`. `meterReadings` doesn't contain consumption but the meter reading (`cumulativeReading`) at the moment of the rollover.
<!-- quelle: code=main.js:2379-2403@v0.6.1 -->

If "Weekday" is also switched on, you'll find the days of last week individually under `currentYear.<category>.previousWeek`, e.g. `previousWeek.01_Monday` to `previousWeek.07_Sunday`.
<!-- quelle: code=main.js:2410-2425@v0.6.1; code=main.js:24@v0.6.1 -->

The same values are also in the JSON state `sourceanalytix.0.<device>.statisticsJson`, see [JSON with all values](#json-values-vis).
<!-- quelle: code=lib/statistics-json.js:53-93@v0.6.1 -->

**From v0.7.0**, the source detail in the instance settings shows these values in the "Values" table, with the rows "Yesterday", "Last week", "Last month", "Last quarter" and "Last year" for consumption and costs.
<!-- quelle: code=src-admin/src/SourceDetail.tsx:61-82; code=src-admin/src/SourceDetail.tsx:329-372; code=src-admin/src/i18n/de.json:183-191; code=main.js:4509-4525; issue=#1269 -->

### When they are filled

At the period rollover, SourceAnalytix copies the value of the current period into the matching previous-period state, for example `01_currentDay` to `01_previousDay`. The current period then starts at 0 again.
<!-- quelle: code=main.js:2379-2403@v0.6.1; code=main.js:2752-2787@v0.6.1; code=main.js:2537-2605@v0.6.1 -->

| State | First filled |
|---|---|
| `01_previousDay` | after the first midnight |
| `02_previousWeek` | on the first Monday at 0:00 (weeks start on Monday) |
| `03_previousMonth` | on the 1st of the next month at 0:00 |
| `04_previousQuarter` | on January 1, April 1, July 1 or October 1 at 0:00 |
| `05_previousYear` | on January 1 at 0:00 |
<!-- quelle: code=main.js:2650-2686@v0.6.1; code=lib/calculation.js:72-82@v0.6.1; forum=635881; forum=660342; issue=#463 -->

Until the first rollover, the states contain 0. That is not an error. The rollover follows the clock of the machine or container that ioBroker runs on.
<!-- quelle: code=main.js:2650-2686@v0.6.1; interview=13b; forum=635881 -->

The value is exactly what the current period held at the time of the rollover. If you enabled a datapoint in the middle of the week and didn't enter [start values](../01.erste-schritte/02.erster-zaehler.md#start-values-unit), the first `02_previousWeek` only contains the days since activation.
<!-- quelle: code=main.js:2752-2787@v0.6.1 -->

If ioBroker was down at midnight, SourceAnalytix catches up the rollover at the next start. It also checks every hour whether a rollover is missing. For more, see [Catching up the day rollover](../02.anleitungen/05.betrieb-und-wartung.md#iobroker-was-down-midnight-recover).
<!-- quelle: code=main.js:2121@v0.6.1; code=main.js:2663-2672@v0.6.1 -->

### Timestamps

Since v0.5.5, the previous-period states don't carry the time of the rollover. They carry 23:59:59 on the last day of the period they belong to. So yesterday's value has the timestamp yesterday 23:59:59. This way, history adapters and charts plot the value in the correct period.
<!-- quelle: code=lib/calculation.js:131-143@v0.6.1; code=main.js:2766-2770@v0.6.1; issue=#497 -->

> [!WARNING]
> If ioBroker was down for several days, `01_previousDay` doesn't hold yesterday's consumption after the start, but that of the last day SourceAnalytix still counted. The timestamp is still yesterday 23:59:59. There are no separate values for the days in between. After a longer outage, check the values in the history adapter.
<!-- quelle: code=main.js:2537-2605@v0.6.1; code=lib/calculation.js:72-82@v0.6.1; code=lib/calculation.js:131-143@v0.6.1; code=main.js:2121@v0.6.1 -->

Because the timestamp lies in the past, a history adapter may treat the value differently from an ordinary new value. If the rollover is caught up later in the day, the value still gets the timestamp of yesterday 23:59:59.
<!-- quelle: code=lib/calculation.js:131-143@v0.6.1; code=main.js:2537-2605@v0.6.1 -->

### If the states are missing or stay empty

1. Open the SourceAnalytix instance settings, "Main settings" tab, "Current year" section.
2. Check that "Previous period" is switched on (default: on). For the individual weekdays of last week, "Weekday" must also be on.
3. Check on the source whether "Consumption" or "Costs" is switched on (from v0.7.0 in the source detail, up to v0.6.x in the custom settings dialog of the datapoint under "Calculate consumption" and "Calculate costs"). Previous-period states are only created for these folders.
4. Wait for the next period rollover. Until then, the state contains 0.
<!-- quelle: code=admin/jsonConfig.json:47-101@v0.6.1; code=io-package.json:266-270@v0.6.1; code=main.js:2101-2110@v0.6.1; code=main.js:2390-2397@v0.6.1 -->

<!-- bild: Instanz-Einstellungen, Reiter „Haupteinstellungen", Bereich „Laufendes Jahr" mit „Vorheriger Zeitraum" (entsteht in Phase 5) -->

> [!WARNING]
> If you switch "Previous period" off, SourceAnalytix deletes the previous-period states the next time the instance starts. If you switch it on again, they start at 0 and are only filled again at the next rollover. Recordings in a history adapter are kept.
<!-- quelle: code=main.js:26@v0.6.1; code=main.js:2101-2110@v0.6.1; code=main.js:2930-2943@v0.6.1 -->

**From v0.6.2:** If ioBroker or the datapoint was down over midnight, SourceAnalytix splits the consumption of the gap between both days by time. As soon as the first value arrives after the outage, the share that falls on the old day is added to `01_previousDay` afterwards (and, at a week, month or year rollover, to the other previous periods). Up to v0.6.1, the whole gap counted toward the new day ([#1260](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1260)).
<!-- quelle: issue=#1260; pr=#1274; interview=11a -->

**From v0.6.2:** For power sources in W, the energy up to midnight is credited to the ending day. Up to v0.6.1, it was lost at every rollover, so `01_previousDay` was slightly too low ([#1254](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1254)).
<!-- quelle: issue=#1254; pr=#1274; interview=6 -->

## Which week, month and quarter states and weekdays are there?

<!-- abschnitt: prio=B; gewicht=16; readme=partial; cluster=periods-21,periods-25; features=current-year-weekday,current-year-weeks,current-year-months,current-year-quarters,year-statistics-archive,rollover-midnight-cron,rollover-missed-recovery-start,rollover-hourly-safety-check,rollover-recover-periods-button,rollover-sendto-recoverperiods,rollover-previous-timestamps,rollover-year-change,rollover-weekday-reset -->
<!-- muss beantworten: State-Baum des laufenden Jahres, Wochentage Mo-So, letzte 7 Tage. -->

**In short:** Under `sourceanalytix.0.<device>.currentYear.<category>`, besides day, week, month, quarter and year, you can optionally get the values of each weekday, each calendar week, each month and each quarter of the current year. You choose which ones exist in the instance settings on the "Main settings" tab, in the "Current year" section. Rolling values like "the last 7 days" don't exist.
<!-- quelle: code=lib/calculation.js:393-433; code=admin/jsonConfig.json:238-293; code=main.js:2252-2264 -->

### The tree of the current year

```text
sourceanalytix.0.<device>
├── cumulativeReading
├── statisticsJson
└── currentYear
    └── <category>
        ├── 01_currentDay … 05_currentYear
        ├── 01_previousDay … 05_previousYear
        ├── currentWeek.01_Monday … 07_Sunday
        ├── previousWeek.01_Monday … 07_Sunday
        ├── weeks.01 … 53
        ├── months.01_January … 12_December
        └── quarters.Q1 … Q4
```
<!-- quelle: code=main.js:24-28; code=main.js:2252-2321; code=lib/calculation.js:393-433 -->

`<category>` is `consumed` or `delivered` (consumption or feed-in), `costs` or `earnings` (costs or earnings) and `meterReadings` (meter readings). Under `meterReadings` there are no `0X_current…` states. The current reading is in `cumulativeReading`.
<!-- quelle: code=main.js:2158-2161; code=main.js:3280-3293 -->

| States | Content | Option under "Current year" | Reset to 0 |
|---|---|---|---|
| `01_currentDay` to `05_currentYear` | current day, week, month, quarter, year | always present | at the period rollover |
| `01_previousDay` to `05_previousYear` | completed previous period | "Previous period" | never, overwritten at the next rollover |
| `currentWeek.01_Monday` to `07_Sunday` | value of each day of the current week | "Weekday" | Mondays at 0:00 |
| `previousWeek.01_Monday` to `07_Sunday` | value of each day of the previous week | "Weekday" and "Previous period" | never, overwritten on Mondays |
| `weeks.01` to `53` | value of the calendar week per ISO 8601, Monday to Sunday | "Weeks" | on January 1 |
| `months.01_January` to `12_December` | value of the month | "Months" | on January 1 |
| `quarters.Q1` to `Q4` | value of the quarter | "Quarters" | on January 1 |
<!-- quelle: code=lib/calculation.js:393-433; code=main.js:1212-1240; code=main.js:2586-2632; code=main.js:2639-2655; code=main.js:2778-2788; code=admin/i18n/de.json:40; code=admin/i18n/de.json:52; code=admin/i18n/de.json:62; code=admin/i18n/de.json:81-82 -->

The weekdays are called `01_Monday`, `02_Tuesday`, `03_Wednesday`, `04_Thursday`, `05_Friday`, `06_Saturday` and `07_Sunday`, the months `01_January` to `12_December`. There are always 53 week states, even in years with 52 calendar weeks. The days from December 29 to 31 that already belong to week 01 of the new year are not under `weeks`, see [Why does week 52/53 show values in the new year?](../05.hintergrund/03.perioden-und-zeit.md#week-52-53-have-values).
<!-- quelle: code=main.js:26-27; code=lib/calculation.js:412-419; code=main.js:1219; code=main.js:4022-4024 -->

### Keeping values beyond the year

On January 1, SourceAnalytix resets `weeks`, `months` and `quarters` under `currentYear` to 0. To keep the values of previous years, switch on "Weeks", "Months" or "Quarters" in the "Year statistics" section. SourceAnalytix then creates a separate folder for each year, `sourceanalytix.0.<device>.<year>.<category>.weeks`, `.months` or `.quarters`, which is kept. For more, see [What happens at the turn of the year?](#happens-turn-year).
<!-- quelle: code=main.js:2639-2655; code=main.js:2216-2235; code=main.js:1242-1244; code=admin/jsonConfig.json:201-237 -->

### The last 7 days

SourceAnalytix doesn't calculate a rolling value over the last 7 days. `currentWeek.<weekday>` holds the days of the current week from Monday, and `previousWeek.<weekday>` holds the days of the whole previous week. For the last 7 days, take the matching days from both folders. Hourly and rolling values are planned ([#424](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/424)).
<!-- quelle: code=main.js:2617-2632; code=lib/calculation.js:393-408; interview=Funktionswünsche; issue=#424 -->

### When the rollover happens

SourceAnalytix switches periods at 0:00 according to the system clock. It also checks every hour and at startup whether a rollover is missing, and catches it up. From v0.7.0 you can also do this by hand with the "Recover periods" action on a source or with the state `info.recoverPeriods`, see [ioBroker was down at midnight](../02.anleitungen/05.betrieb-und-wartung.md#iobroker-was-down-midnight-recover).
<!-- quelle: code=main.js:3011-3035; code=main.js:2323-2324; code=main.js:2527-2537; code=src-admin/src/SourceDetail.tsx:630-637; interview=13b -->

**From v0.6.2:** The week archive in the year folder follows the year of the ISO calendar week. Week 01, which already starts at the end of December, ends up in the folder of the new year and no longer overwrites week 01 of the old year ([#1256](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1256)).
<!-- quelle: issue=#1256; code=main.js:4026-4035; code=main.js:2243-2246 -->

## Is there a JSON with all values (for VIS)?

<!-- abschnitt: prio=B; gewicht=9; readme=covered; cluster=outputs-viz-19,prices-costs-23; features=output-statistics-json,output-basic-period-states,output-cost-vs-earnings,output-tree-layout -->
<!-- muss beantworten: Aufbau von statistics-JSON und Tabelle. -->

**In short:** Yes. Every source has the state `sourceanalytix.0.<device>.statisticsJson`. It contains all values of the current year as one JSON: consumption, costs and meter readings, each for the current periods, the previous periods, and the weekdays, weeks, months and quarters. You don't have to switch anything on for it.
<!-- quelle: code=main.js:1251-1272; code=main.js:1288-1306; code=lib/statistics-json.js:53-89 -->

### Structure

A shortened example for an electricity source:

```json
{
  "schemaVersion": 1,
  "year": 2026,
  "source": { "id": "<datapoint ID>", "name": "Strom Haus", "unit": "kWh" },
  "quantity": {
    "type": "consumed",
    "current": { "day": 4.2, "week": 31.7, "month": 120.4, "quarter": 410.9, "year": 2950.3 },
    "previous": { "day": 5.1, "week": 33.2, "month": 140.8, "quarter": 420.5, "year": 3510.6 },
    "periods": {
      "weekdays": { "1": 5.3, "2": 4.2 },
      "previousWeekdays": { "1": 4.9, "2": 5.0, "3": 4.4, "4": 4.6, "5": 4.8, "6": 5.2, "7": 4.3 },
      "weeks": { "45": 33.2, "46": 31.7 },
      "months": { "10": 140.8, "11": 120.4 },
      "quarters": { "3": 420.5, "4": 410.9 }
    }
  },
  "financial": {
    "type": "costs",
    "currency": "€",
    "current": { "day": 1.34, "week": 10.14, "month": 38.53, "quarter": 131.49, "year": 944.1 },
    "previous": { "day": 1.63, "week": 10.62, "month": 45.06, "quarter": 134.56, "year": 1123.39 },
    "periods": { "weekdays": {}, "previousWeekdays": {}, "weeks": {}, "months": {}, "quarters": {} }
  },
  "meterReadings": {
    "current": 48213.4,
    "previous": { "day": 48209.2, "week": 48181.7, "month": 48093, "quarter": 47802.5, "year": 45263.1 },
    "periods": { "weekdays": {}, "previousWeekdays": {}, "weeks": {}, "months": {}, "quarters": {} }
  }
}
```
<!-- quelle: code=lib/statistics-json.js:21-89; code=lib/statistics-json.js:120-189 -->

| Field | Content |
|---|---|
| `schemaVersion` | Version of the structure, currently `1` |
| `year` | the current year |
| `source` | `id` of the datapoint, `name` of the source, `unit` = target unit |
| `quantity` | Consumption (`type`: `consumed`) or feed-in (`delivered`); `null` if "Consumption" is off |
| `financial` | Costs (`costs`) or earnings (`earnings`) with `currency`; `null` if "Costs" is off |
| `meterReadings` | Meter readings; `current` is the total from `cumulativeReading`; `null` if "Store meter readings" is off |
| `current` | current periods `day` to `year`, from `01_currentDay` to `05_currentYear` |
| `previous` | previous periods from `01_previousDay` to `05_previousYear`; `null` if "Previous period" is off |
| `periods.weekdays`, `periods.previousWeekdays` | weekdays of the current and the previous week, keys `1` (Monday) to `7` (Sunday) |
| `periods.weeks` | calendar weeks, keys `01` to `53` |
| `periods.months` | months, keys `01` to `12` |
| `periods.quarters` | quarters, keys `1` to `4` |
<!-- quelle: code=lib/statistics-json.js:21-89; code=lib/statistics-json.js:120-189; code=main.js:1251-1272 -->

A group under `periods` is `null` if the option under "Current year" is off. A value that doesn't exist yet is missing or `null`. The year archive (`<ID>.<year>`) is not part of the JSON.
<!-- quelle: code=lib/statistics-json.js:21-46; code=lib/statistics-json.js:105-113; code=lib/statistics-json.js:147-189 -->

### When it is written

SourceAnalytix collects the changes of a value and writes the JSON at most every 300 ms, and only if the content has changed. At startup, it rebuilds the JSON from the existing states. If the source is deactivated, the last JSON stays in place but is no longer updated. The state is read-only (`role` `json`).
<!-- quelle: code=main.js:1312-1337; code=main.js:1354-1378; code=main.js:1384-1391; code=main.js:1288-1306 -->

> [!TIP]
> In a script, read the JSON with `JSON.parse(getState('sourceanalytix.0.<device>.statisticsJson').val)`. That way, a table in VIS needs only one state instead of many individual ones.
<!-- quelle: code=main.js:1288-1306; code=lib/statistics-json.js:195-197 -->

## What happens at the turn of the year?

<!-- abschnitt: prio=B; gewicht=8; readme=partial; cluster=periods-20; features=year-statistics-archive,rollover-year-change,current-year-previous,price-scheduled-valid-from -->
<!-- muss beantworten: Vorjahreswerte, neue Ordner, Jahresarchiv. -->

**In short:** On January 1 at 0:00, the year value moves to `05_previousYear`, all current periods start at 0, and the weeks, months and quarters under `currentYear` are reset to 0. The total `cumulativeReading` keeps running. You only keep the monthly and weekly values of the old year with "Year statistics", in a year folder of their own.
<!-- quelle: code=main.js:2745-2800; code=main.js:2639-2655; code=main.js:2586-2610; code=main.js:2216-2235 -->

### What happens at the rollover

1. Day, week, month, quarter and year roll over at the same time. With "Previous period", SourceAnalytix copies the values to `01_previousDay` through `05_previousYear`, with the timestamp December 31, 23:59:59.
2. The start values of all periods are set to the current total. `01_currentDay` to `05_currentYear` start at 0.
3. `weeks`, `months` and `quarters` under `currentYear` are set to 0 for consumption, costs and meter readings.
4. If "Weeks", "Months" or "Quarters" is on under "Year statistics", SourceAnalytix creates the folder `sourceanalytix.0.<device>.<new year>` with these states and the annual totals (`consumedCumulative`, `costsCumulative`, `readingCumulative`).
5. The year folders of previous years stay unchanged.
<!-- quelle: code=main.js:2770-2788; code=main.js:2586-2610; code=main.js:2639-2655; code=main.js:2216-2235; code=lib/calculation.js:290-310 -->

> [!WARNING]
> Without "Year statistics", the monthly, weekly and quarterly values of the old year can only be found in a history adapter after the rollover. By default, "Months" is on, and "Weeks" and "Quarters" are off.
<!-- quelle: code=main.js:2639-2655; code=io-package.json:274-276 -->

You can safely delete old year folders if you no longer need them. SourceAnalytix only writes to the folder of the current year.
<!-- quelle: interview=8; code=main.js:1170-1180; code=main.js:1242-1244; code=main.js:3703-3718 -->

### Prices at the turn of the year

If a price is "Valid from" January 1, SourceAnalytix uses it from 0:00. The basic fee is booked in full on January 1, as on the first of every month. **From v0.6.2**, `priceDefinitions.<category>.currentPrice` also jumps to the new price at that moment. Up to v0.6.1, this only happened after a restart ([#1259](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1259)).
<!-- quelle: code=lib/dynamic-pricing.js:40-54; code=lib/calculation.js:632-672; code=main.js:3132-3149; code=main.js:3061; issue=#1259 -->

If ioBroker was down at the turn of the year, SourceAnalytix catches up the rollover at the next start, see [ioBroker was down at midnight](../02.anleitungen/05.betrieb-und-wartung.md#iobroker-was-down-midnight-recover).
<!-- quelle: code=main.js:2323-2324; code=main.js:2745-2760 -->

**From v0.6.2:** The days from December 29 to 31 that belong to calendar week 01 of the new year end up in the week archive of the new year ([#1256](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1256)).
<!-- quelle: issue=#1256; code=main.js:4026-4035 -->

<a id="prices-read-written-as-states"></a>

## How can I read and set prices as states?

<!-- abschnitt: prio=B; gewicht=6; readme=covered; cluster=prices-costs-03; features=price-current-price-writable,price-history-states,output-info-price-states -->
<!-- muss beantworten: Preis-States, Historie, info-Preis-States. -->

**In short:** For every price definition there are states under `sourceanalytix.0.priceDefinitions.<category>` with the current and the configured price. `currentPrice` is writable: if you write a new price to it, it applies immediately to all sources of that price definition.
<!-- quelle: code=main.js:356-393; code=main.js:467-484; code=main.js:2510-2520 -->

| State | Content | Writable |
|---|---|---|
| `priceDefinitions.<category>.currentPrice` | Price per unit that currently applies, in `<currency>/<unit>` | yes |
| `priceDefinitions.<category>.configuredPrice` | "Price per unit" from the table, only for "Fixed price" | no |
| `priceDefinitions.<category>.configuredPriceValidFrom` | from when this price applies, as a timestamp in milliseconds | no |
| `priceDefinitions.<category>.configuredBasicPrice` | "Price per month" from the table | no |
| `priceDefinitions.<category>.configuredBasicPriceValidFrom` | from when the basic fee applies | no |
| `priceHistory.<category>` | Price history as JSON, for example `[{"ts":1767222000000,"price":0.32}]` | no |
| `basicPriceHistory.<category>` | History of the basic fee as JSON | no |
<!-- quelle: code=main.js:340-393; code=main.js:401-425; code=main.js:467-484; code=main.js:515-530; code=main.js:571-590; code=main.js:649-675; code=lib/dynamic-pricing.js:83-106 -->

In state IDs, SourceAnalytix replaces every character of the category other than letters, digits, `_` and `-` with `_`. So `Strom Haus` becomes `priceDefinitions.Strom_Haus.currentPrice`.
<!-- quelle: code=main.js:340-393 -->

### Setting the price via `currentPrice`

1. Write the new price per unit as a number to `sourceanalytix.0.priceDefinitions.<category>.currentPrice`, without acknowledgment (`ack` = false), for example from a script: `setState('sourceanalytix.0.priceDefinitions.Strom.currentPrice', 0.29);`
2. SourceAnalytix applies it to all sources of that price definition, stores it with the time in the price history and writes `Unit price for <category> was set to <price> through <state>` to the log.
3. If the value is not a number, the old price stays, and the log shows `Writable price state <state> received invalid value …`.
<!-- quelle: code=main.js:2510-2520; code=main.js:2541-2545; code=main.js:491-502; code=lib/dynamic-pricing.js:7-17 -->

The new price applies from the moment of writing. It doesn't change costs that have already been calculated. For that, v0.7.0 and later have the "Recalculate costs from date" action, see [Are calculated costs recalculated when I change the price, and how do I change it from a certain date?](../02.anleitungen/03.preise-und-kosten.md#costs-recalculated-change-price-change).
<!-- quelle: code=main.js:2516-2518; code=lib/dynamic-pricing.js:140-154; issue=#947 -->

> [!NOTE]
> With "Price source" set to "State value" or "Tariff selector", the next value of the price datapoint overwrites a price you wrote by hand. If you change the "Price per unit" in the table and save, that price applies again.
<!-- quelle: code=main.js:2478-2500; code=main.js:401-445 -->

<a id="meter-readings-cumulative"></a>

## Why are meter readings cumulative?

<!-- abschnitt: prio=B; gewicht=3; readme=partial; cluster=periods-30; features=output-cumulative-reading,current-year-previous,output-tree-layout -->
<!-- muss beantworten: Meter-Readings-Ordner und cumulativeReading erklärt. -->

**In short:** Under `meterReadings` you find meter readings, not consumption. Each state shows the total at the end of its period. That's why the value grows from month to month. You find the consumption of a period under `consumed` (or `delivered`).
<!-- quelle: code=main.js:3667-3718; code=main.js:2605-2607 -->

### `cumulativeReading` and `meterReadings`

| State | Content |
|---|---|
| `sourceanalytix.0.<device>.cumulativeReading` | The total: SourceAnalytix's own meter reading in the target unit, unrounded. It is written with every new value. |
| `currentYear.meterReadings.months.<month>`, `.weeks.<NN>`, `.quarters.Q<n>`, `.currentWeek.<weekday>` | The total, rounded, as last written in this period. It stays in place after the period ends, so it is the reading at the end of the period. |
| `currentYear.meterReadings.01_previousDay` to `05_previousYear` | The total at the moment of the period rollover |
| `<year>.meterReadings.…` and `<year>.readingCumulative` | The same in the year archive, if "Year statistics" is on |
<!-- quelle: code=main.js:3632-3645; code=main.js:3667-3718; code=main.js:2605-2607; code=main.js:2232-2235 -->

Example: if `meterReadings.months.02_February` holds 1,250 kWh and `meterReadings.months.03_March` holds 1,480 kWh, you consumed about 230 kWh in March. The exact value is in `consumed.months.03_March`.
<!-- quelle: code=main.js:3667-3718; code=main.js:1226-1231 -->

The total includes the offset from reset detection. After a device reset, `cumulativeReading` therefore keeps showing the continuous reading, not the value the device currently reports. The terms are explained in [What does "Device reset detected" mean and how does reset detection work?](../05.hintergrund/02.zaehler-reset.md#device-reset-detected-mean-reset). If you want the total to match your real meter, use the "Align meter reading" action from v0.7.0, see [Correcting wrong values](../02.anleitungen/02.zaehlerstaende-korrigieren.md#correct-wrong-too-high-negative).
<!-- quelle: code=lib/calculation.js:444-454; code=main.js:3555-3604; code=main.js:4124-4185; issue=#640 -->

`meterReadings` is only created if "Store meter readings" is on for the source. For when the folder stays empty, see [What do the datapoint settings do (Costs, Consumption, Meter values)?](01.einstellungen.md#datapoint-settings-costs-consumption-meter).
<!-- quelle: code=main.js:3280-3293; code=main.js:3667 -->

**From v0.6.2:** A meter reading of exactly 0 is now also written under `meterReadings`. Up to v0.6.1, the state stayed empty in that case ([#1253](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1253)).
<!-- quelle: issue=#1253; code=main.js:3672 -->

**See also:** [How is consumption calculated, and why is currentYear lower than my meter reading?](../05.hintergrund/01.berechnung.md#consumption-calculated-currentyear-lower-than) · [How do I apply my real meter reading (cumulativeReading, RAW object)?](../02.anleitungen/02.zaehlerstaende-korrigieren.md#apply-real-meter-reading-cumulativereading) · [JSON with all values](#json-values-vis)

<a id="currency-sourceanalytix-use"></a>

## Which currency does SourceAnalytix use?

<!-- abschnitt: prio=B; gewicht=2; readme=missing; cluster=prices-costs-11; features=calc-currency -->
<!-- muss beantworten: Währung der Kosten und Grenzen (nur eine Währung). -->

**In short:** The currency from the ioBroker system settings. If none is set there, SourceAnalytix uses `€`. There is only one currency for all sources, and SourceAnalytix doesn't convert: the currency is just the unit on the cost states.
<!-- quelle: code=main.js:106-112; code=main.js:3296-3300; code=main.js:477 -->

- The currency is the unit on all states under `costs` and `earnings`, on the annual totals `costsCumulative` and `earningsCumulative`, and appears as `<currency>/<unit>` on `priceDefinitions.<category>.currentPrice`.
- You enter all prices in the price definitions in this currency, per target unit, so for example in €/kWh and not in cents/kWh.
- A price datapoint must also deliver the price in this currency per target unit. There is no conversion factor, for example from cents to euros. Convert beforehand, for example with an alias or a script.
<!-- quelle: code=main.js:3296-3300; code=main.js:2234; code=main.js:477; code=main.js:1434-1440; code=lib/dynamic-pricing.js:7-17 -->

> [!IMPORTANT]
> SourceAnalytix only reads the currency at startup. If you change it in the system settings, restart the instance. Amounts that have already been calculated are not converted.
<!-- quelle: code=main.js:106-112 -->

**See also:** [How is a price definition structured (categories, basic fee, decimal mark)?](01.einstellungen.md#price-definition-structured-categories-base) · [How can I read and set prices as states?](#prices-read-written-as-states)

## sendTo commands and info states

<!-- abschnitt: prio=B; gewicht=0; readme=missing; cluster=; features=msg-getpricedefinitions,msg-getunits,msg-getusedoutputids,msg-recoverperiods,info-recoverperiods-state,info-no-connection-state -->
<!-- muss beantworten: recoverPeriods, info-States, fehlende info.connection. -->

**In short:** SourceAnalytix accepts commands via `sendTo`. The settings page from v0.7.0 uses them itself, and you can also call them from scripts, for example `recoverPeriods` for a missed period rollover or `setCumulative` to align the meter reading. There are only two instance states: `info.recoverPeriods` and `info.costRecalculation`. There is no `info.connection` state.
<!-- quelle: code=main.js:4711-4787; code=main.js:4681-4708; code=main.js:3153-3173; code=main.js:4248-4261; code=io-package.json:142; code=io-package.json:288 -->

### Commands

All values are in the target unit of the source. Numbers may use a comma or a dot. `source` is always the ID of the source datapoint. With `dryRun: true`, SourceAnalytix only validates and returns a preview without changing anything.

| Command | Parameters | What it does |
|---|---|---|
| `recoverPeriods` | `{source}` (optional, from v0.7.0) | Catches up missed day, week, month, quarter and year rollovers, with `source` only for this source, otherwise for all. Response: `{recovered: <number of sources>}`, for an inactive source `{error: 'sourceNotActive'}` |
| `getSources` / `checkProblems` | – | Returns all sources with values, the problems, the price definitions, the units and the currency (both commands return the same) |
| `saveSource` | `source`, `settings`, `dryRun` | Creates or changes the SourceAnalytix settings of a datapoint. `settings` contains only the fields that change, for example `{deviceResetLogicEnabled: true}`. Takes effect without a restart. |
| `setSourceEnabled` | `source`, `enabled` | Activates (`true`) or deactivates (`false`) a source. The data stays. |
| `findCandidates` | `query` | Searches for datapoints with a supported unit (50 at most), for the wizard |
| `setCumulative` | `source`, `value`, `dryRun` | "Align meter reading": sets the total to `value` |
| `meterSwap` | `source`, `oldEnd`, `newStart`, `date`, `dryRun` | "Meter swapped": end reading of the old meter, start reading of the new one (empty = 0), date for information only. Not for power sources. |
| `recalcCosts` | `source` or `priceDefinition`, `from`, `dryRun` | "Recalculate costs from date" for one source or all sources of a price definition. `from` as a timestamp in ms or a date, not in the future. |
| `deleteSourceData` | `source` or `outputId`, `dryRun` | "Delete data": deactivates the source, removes its SourceAnalytix settings and deletes its folder. With `outputId`, it also works for folders without a datapoint. |
<!-- quelle: code=main.js:4681-4708; code=main.js:4711-4787; code=main.js:4550-4600; code=main.js:4609-4617; code=main.js:4624-4653; code=main.js:4659-4673; code=main.js:4124-4185; code=main.js:4192-4240; code=main.js:4273-4362; code=main.js:4373-4420; code=main.js:4096-4099; code=lib/source-actions.js:33-65 -->

SourceAnalytix also answers `getPriceDefinitions`, `getUnits`, `getStartValueContext`, `getBasicRateSources` and `getUsedOutputIds`. The wizard uses `getUsedOutputIds` to check whether a technical ID is already taken. The other commands used to fill selection lists and checks in the custom settings dialog of the datapoint, which from v0.7.0 only contains the switch to enable the source ([#1286](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1286)).
<!-- quelle: code=main.js:4715-4756; code=src-admin/src/Wizard.tsx:116; code=admin/jsonCustom.json:1-55; issue=#1286 -->

Example: align the meter reading, first as a preview.

```js
sendTo('sourceanalytix.0', 'setCumulative', { source: '<datapoint ID>', value: 12475, dryRun: true }, result => {
    log(JSON.stringify(result));
});
```
<!-- quelle: code=main.js:4681-4706; code=main.js:4124-4146 -->

If something goes wrong, the response contains `error` and `message`, for example `sourceNotActive` if the source isn't running, `invalidValue` for an invalid number or `invalidDate` for a date in the future. For invalid fields, `saveSource` returns `invalidSettings` and lists the affected fields under `errors`.
<!-- quelle: code=main.js:4106-4112; code=lib/source-actions.js:33-65; code=main.js:4691-4692; code=main.js:4584; code=main.js:4775-4780 -->

> [!CAUTION]
> `deleteSourceData` without `dryRun` deletes the folder of the source with all values and years and removes its settings on the datapoint. This cannot be undone.
<!-- quelle: code=main.js:4373-4420; code=src-admin/src/i18n/de.json:74-79 -->

### Info states

| State | Content |
|---|---|
| `sourceanalytix.0.info.recoverPeriods` | Button (`role` `button`). If you write `true` to it, SourceAnalytix catches up missed period rollovers and resets the state to `false`. This also works while SourceAnalytix is otherwise not calculating. |
| `sourceanalytix.0.info.costRecalculation` | Progress of "Recalculate costs from date" as JSON: `running`, `done`, `total`, `from`, `sources`, `ts`. Only created the first time you recalculate (from v0.7.0). |
<!-- quelle: code=main.js:30-31; code=main.js:3153-3173; code=main.js:2527-2537; code=main.js:4248-4261; code=main.js:4300-4308 -->

SourceAnalytix doesn't create an `info.connection` state, because there is no connection to a device that it could report. If it's missing from the object list, that is not an error.

<a id="migrating-older-versions-legacy-settings"></a>

## Migrating from older versions and legacy settings

<!-- abschnitt: prio=B; gewicht=0; readme=missing; cluster=; features=migration-output-id-change,migration-output-id-recovery,migration-output-id-default,migration-rounding-per-source,migration-legacy-cumulative-states,migration-dynamic-cost-v2,migration-legacy-native-keys -->
<!-- muss beantworten: Output-ID-Migration, unterbrochene Migration, alte native Schlüssel. -->

**In short:** SourceAnalytix takes over data from older versions by itself at startup. You don't have to do anything. Some old settings still exist in the instance, but they no longer have any effect.
<!-- quelle: code=main.js:3947-3981; code=main.js:1932-1955; code=lib/output-id.js:14-26; code=io-package.json:273-285 -->

### What SourceAnalytix changes at startup

| What | What happens |
|---|---|
| Technical ID (output ID) | If a source doesn't have one yet, SourceAnalytix uses the previous ID (datapoint ID with `__` instead of dots) and writes it to the settings of the source. The folder stays where it is. |
| Decimals | If a source has no decimals of its own, it gets the instance template once and keeps it afterwards, see [Decimals](01.einstellungen.md#instance-settings-exist-periods-decimals). |
| Total from very old versions | If `cumulativeReading` is missing or 0, SourceAnalytix reads the reading from `<ID>.Current_Reading` or `<ID>.Meter_Readings.Current_Reading` of old versions. |
| Cost memory | An old cost memory that included the basic fee is converted so that the basic fee isn't counted twice after a restart (`Migrated dynamic cost memory for <datapoint> to variable-cost schema version 2`). |
<!-- quelle: code=lib/output-id.js:14-26; code=main.js:1932-1955; code=main.js:2000-2009; code=main.js:3947-3981; code=main.js:900-915 -->

### Moving the technical ID

If you change the technical ID, SourceAnalytix copies the folder, checks the copy and then deletes the old folder, see [How do I name the datapoint (alias, output ID)?](01.einstellungen.md#name-datapoint-alias-output-id). If the instance stops in the middle, SourceAnalytix removes an incomplete copy at the next start and tries again (`Removed incomplete output migration … will be retried`), or it cleans up the old folder after a verified copy (`Completed pending output migration cleanup …`).
<!-- quelle: code=main.js:1580-1605; code=main.js:1810-1890 -->

### Old settings without effect

The instance data still contains `store_days`, `store_years`, `store_period`, `keep_days`, `keep_weeks`, `keep_months`, `keep_quarters`, `keep_years`, `impuls` and `status_logging`. No user interface shows them, and SourceAnalytix doesn't read them. Options such as "Status messages to log" or "Number of days" from old forum posts no longer exist. From v0.7.0, you set up pulse counters on the source, see [Pieces and pulses](01.einstellungen.md#units-supported-energy-volume-weight).
<!-- quelle: code=io-package.json:273-285; code=admin/jsonConfig.json:1-334; code=admin/i18n/de.json:73; code=admin/i18n/de.json:88; code=src-admin/src/SourceDetail.tsx:473-484; code=src-admin/src/SourceDetail.tsx:560-570; issue=#74; issue=#1285 -->

**From v0.6.2:** The old stored value `valueAtDeviceInit` is no longer needed ([#1263](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1263)). From v0.7.0, the settings page hides it, `valueAtDeviceReset` and `pendingMeterSwap`, and never overwrites them. Only SourceAnalytix itself or an action such as "Align meter reading" changes these values.

## Other (unfinished/internal functions)

<!-- abschnitt: prio=B; gewicht=0; readme=missing; cluster=; features=other-sentry-plugin,other-impulse-counter-unfinished,other-vis-widget-json-unfinished,other-cleanup-unused-unfinished,other-period-placeholder-unfinished,other-object-subscription,other-console-debug -->
<!-- muss beantworten: VIS-Widget-JSON, Debug-Ausgabe. -->

**In short:** A few things in the code are internal or unfinished. What matters to you: there is no separate VIS widget JSON, use `statisticsJson`. Debug output of the price and unit definitions doesn't go to the ioBroker log but to the console of the process.
<!-- quelle: code=main.js:3796-3802; code=main.js:1476 -->

| Function | Status |
|---|---|
| VIS widget JSON | Commented-out code only. All values for VIS are in [`statisticsJson`](#json-values-vis). |
| Debug output | At startup, SourceAnalytix writes the loaded units and prices with `console.debug` to the standard output of the process, for example to the Docker or systemd log, regardless of the log level. It doesn't appear in the ioBroker log. |
| Error reports (Sentry) | SourceAnalytix reports errors in the code to the developer through the ioBroker Sentry plugin, if the plugin is active. |
| Pulse counters | Up to v0.6.x only a placeholder in the code. From v0.7.0 there are `piece`, `piece/min` and "Pulses per unit of the price definition", see [Pieces and pulses](01.einstellungen.md#units-supported-energy-volume-weight). |
| Cleaning up old folders | There is no automatic cleanup. From v0.7.0 you delete the folder of a source with the "Delete data" action. Folders whose datapoint is missing are shown in the "Overview" as "Folder without datapoint" ([#1265](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/1265)). |
| Custom periods | A placeholder in the code (`reading_start = 0`) is meant for freely selectable billing periods. They are not implemented but planned ([#595](https://github.com/DrozmotiX/ioBroker.sourceanalytix/issues/595)). |
| Monitoring all objects | SourceAnalytix subscribes to changes of all objects. That way it notices without a restart when you enable or change a source. |
